## 三、架构分层

```
浏览器 ──REST(/api/*)──┐
  ├─ WS /ws/overview   │   api/          rest.py(754) · ws_overview · ws_logs · ws_login · auth · context
  ├─ WS /ws/logs       ├── api/          唯一入口；context.py 模块级单例 ctx 做依赖注入
  └─ WS /ws/login      │
                       ├── services/     wizard.py 五步状态机 · resume.py 面板重启自愈 · login.py
                       ├── adapters/     base.py 契约 + 10 个程序适配器（manifest 驱动）
                       └── core/         process 进程守护 · registry 状态机 · ports · locks
                                         packages 包缓存 · backup 备份 · exports 产物 · scheduler
                                         scanner 游离扫描 · metrics 资源曲线 · firewall · atomicio
```

**关键设计（值得肯定的三点）**

1. **manifest 驱动，零硬编码分支**：程序差异全部落在 `manifests/*.json` 与对应 adapter；  
   `core/api/services` 内不出现程序名判断（rest.py 兼容性校验也走 `compatible_login`）。  
   新增程序 = manifest + adapter + `adapters/__init__.py` 注册一行。
2. **启动命令后端独占构建**：`build_start_cmd` 是唯一权威入口，前端不传 cmd，杜绝任意命令执行。
3. **可重入锁 + 原子写**：`core/locks.py` 用 RLock + 引用计数文件锁（REST 先取 instance_lock 再调  
   registry，registry 内部又取同一把，不可重入会自锁）；所有 JSON 走 `write_atomic`（mkstemp + fsync + os.replace）。

## 四、核心机制拆解

### 4.1 实例状态机（`core/registry.py:14-26`）

`UNDEPLOYED → DEPLOYING → AWAIT_LOGIN → CONFIGURED → RUNNING`，ERROR 可从任意态进入也可恢复。  
删除走**墓碑**（`__tombstone__` 保留 30 天），防止端口/目录被同名实例误抢。

### 4.2 五步向导（`services/wizard.py`）

- 断点续跑：`next_step()` 按当前状态推导下一步；`GET /api/pending` 暴露中间态实例。
- Step4 互联是**最容易出问题的地方**，代码做了三重防护：登录端已删返回 `dangling` 明确报错（不静默生成新 token）；  
  token 由登录端生成、骰子端经 `login_ref` 继承，保证两端一致；官方通道（`bot_mode=official`）直接跳过 Step3/Step4。
- Step5 与 REST start/restart、备份恢复、面板自愈**共用 `Wizard.start_instance`** 一条路径，避免多实现漂移。

### 4.3 进程守护（`core/process.py`）

环形缓冲存 `(seq, line)` 对——WS 回放与实时 hook 用 seq 去重，消除「快照后、hook 前」丢行窗口；  
自动重启为**滑动窗口** 5 次 / 300s，稳定运行超时后清零（修掉了早期「一辈子只守护 5 次」的缺陷），  
熔断后 `crash_looped` 在总览可见。日志双限滚动（50MB / 7 天）+ `os.replace` 原子轮转。

### 4.4 三条 WebSocket 通道

| 通道             | 职责                | 关键实现                                                                              |
| -------------- | ----------------- | --------------------------------------------------------------------------------- |
| `/ws/overview` | 2s 推送拓扑 + 内存水位    | 增量游标 `_scan_cursor` 只扫新增行；`actual_port` / `webui_token` / `qq` 由它延迟回填（启动瞬间日志还没打印） |
| `/ws/logs`     | 日志回放 + 实时 tail    | 先注册 hook 再取快照；支持 pause / filter / 错误行标记                                           |
| `/ws/login`    | 二维码 / 滑块链接 / 完成事件 | 按连接对字符画二维码去重；`refresh` 重启进程、`skip_login` 跳过；AWAIT_LOGIN 且进程未起时自动拉起                |

### 4.5 备份 / 升级 / 回收

- 两种备份口径严格区分：`full` 整目录、`data` 仅 manifest `data_paths`。
- 导入有 **zip-slip 防护 + 顶层目录落位打分**（`core/backup.py:42-91`），先整体校验再落盘，不会解压一半才报错。
- 升级：强制整目录快照 → 停机 → 覆盖解压（包内覆盖、包外保留）→ 拉回运行，失败带备份名回退。
- 回收三通道：包缓存 `DELETE /packages/unused`（带 `in_use`）、备份产物 `DELETE /exports/prune`、  
  实例删除同步删日志与资源曲线 + 启动扫孤儿。
- 定时任务守护（每日重启/备份）`last_day` 持久化，面板重启不重复跑；`_prune` 匹配必须同时带  
  `-sched-` 与 scope，避免误删升级快照或跨口径互删。

### 4.6 鉴权（`api/auth.py`）

随机密码 + PBKDF2(200k) 落盘；**首次启动明文只打印一次且只走 console**（测试 `test_auth_password.py` 锁住该契约）；  
Bearer token 恒定时间比较、30 天 TTL；登录失败 60s/5 次限速；改密轮换 token 使旧会话全失效；  
WS 优先用 `Sec-WebSocket-Protocol` 携带 token（避免 token 落 nginx 日志），兼容 `?token=`。  
启动时 `os.umask(0o077)` + 状态文件 chmod 600。

## 六、部署与运维

- `deploy/install.sh`：一键装依赖 → 拉代码 → venv → 前端构建 → systemd → nginx，支持 `--swap`（2G 机建议）。
- systemd `Restart=always`；实例是面板子进程，故 `services/resume.py` 在 lifespan 后台**只拉回 RUNNING 态**实例  
  （用户主动 stop 落 CONFIGURED 不会被复活），逐个 try/except + 错峰，失败写实例日志，`DM_AUTO_RESUME=0` 可关。
- CI（`.github/workflows/ci.yml`）：ubuntu-24.04 + Python 3.12，跑 ruff / mypy / pytest + 前端 build；  
  actions 与 runner 均固定版本，避免环境突变。

## 十、总体评价

这是一个**工程质量明显高于平均水平的个人/小团队项目**：分层干净、契约明确、安全基线扎实（命令后端构建、  
恒定时间比较、原子写、路径穿越防护、删除守卫），更难能可贵的是代码中保留了大量「为什么这么写」的故障注释，  
说明它是在真实生产事故中迭代出来的，而不是一次性生成物。质量门禁全绿、194 用例覆盖到主要机制。

主要风险不在架构，而在**周边一致性**：两份 manifest 少填了校验字段、README 与安装脚本落后于代码、  
WS 通道缺少自动化回归。这些都是小成本可修项，建议在进入下一轮功能开发前集中清理一轮。
